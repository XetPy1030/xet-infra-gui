# ADR-0006: Внутренняя модульная система с contribution points

**Статус**: принят (2026-07-29)

## Контекст

Сейчас приложение — про Teleport, но план — «личный хаб»: быстрые ссылки (Grafana с
фильтрами), календарь/напоминалки, пространства. Нельзя дать первому домену прорасти в ядро.

## Решение

Лёгкая **внутренняя** модульная система (compile-time, не runtime-плагины):

```ts
interface AppModule {
  id: string;                                  // 'teleport', 'links', 'calendar'…
  actions?: Action[];                          // → ActionRegistry (⌘K, хоткеи)
  trayItems?: TrayContribution[];              // → секции popover
  views?: ViewContribution[];                  // → разделы sidebar главного окна
  settings?: SettingsSection[];                // → экран настроек
  services?: (ports: CorePorts) => Disposable; // фоновые сервисы модуля
}
```

- `ModuleRegistry` собирает contributions при старте; ядро (сессии, IPC, трей-механика,
  палитра) ничего не знает о конкретных доменах.
- **Teleport — первый модуль** и полигон API: всё, что ему нужно от ядра, добавляется как
  generic-механизм, а не как teleport-специальный хук.
- Модуль «links» (Grafana) станет проверкой системы: только декларации, ноль правок ядра.
- Внешний plugin SDK (runtime-загрузка) — сознательно отложен до реальной надобности.

## Последствия

- (+) Новые домены — аддитивны; «работа» и будущая «личная» части не переплетаются.
- (+) Модуль можно выключить в настройках целиком (contributions просто не регистрируются).
- (−) Дисциплина: заметив teleport-специфику в `core/` вне `core/modules/teleport` — выносить.
