# ADR-0007: Логи и one-shot команды kubectl идут через PTY, а не через отдельный spawn

**Статус**: принят (2026-08-01, M2)

## Контекст

[03 §6](../03-architecture.md#6-поток-данных-pty-и-производительность) закладывал для
follow-логов обычный `spawn` («PTY не нужен — не интерактив») со своими батчингом и
`stdout.pause/resume`. При реализации M2 выяснилось:

1. Весь механизм доставки потока в UI (батчинг 12 мс, watermark потока, ring buffer,
   backpressure по ack, снапшот при переоткрытии окна, реестр и FSM сессий) уже живёт в
   `SessionManager` и завязан на `PtyHandle`. Второй канал доставки — это второй реестр,
   второй снапшот и второй набор тех же граблей (docs/04 §7).
2. `tsh kubectl logs/exec` **может** запросить MFA per-session в зависимости от политики
   кластера ([04 §3.3](../04-tsh-integration.md#33-kubernetes)). Не-PTY процесс такой
   интерактивный промпт не переживёт, и пришлось бы всё равно иметь PTY-обёртку как фолбэк.

## Решение

Все kube-потоки — сессии `SessionManager` поверх PTY:

| Команда | Канал | Почему |
|---|---|---|
| `kubectl exec -it … -- bash` | PTY | интерактив по определению (FR-K4) |
| `kubectl logs --tail --follow` | PTY | тот же батчинг/backpressure/ring buffer + переживает промпт MFA |
| `kubectl exec … -- sh -lc '<cmd>'` (one-shot) | exec (`ProcessRunner`) | результат нужен как данные — в панель вывода (FR-K5) |
| one-shot, упёршийся в MFA | PTY | фолбэк: та же команда видимым табом (`kube.execPty`) |
| `kube ls` / `kube login` / `get pods -o json` | exec | структурированные запросы, JSON + zod |

`SessionManager.setPaused` (пауза follow-логов кнопкой) — ручная пауза поверх
flow-control'ной: снятие backpressure-паузы её не отменяет.

## Последствия

- (+) Один путь данных, один реестр сессий, одна история восстановления окна; логи
  бесплатно получают всё, что уже отлажено на login/proxy.
- (+) MFA-промпт в логах закрывается тем же `PromptPipeline`, без отдельной ветки.
- (−) PTY навязывает логам терминальную семантику: перевод строк `\n` → `\r\n`, размер
  окна влияет на переносы. Для просмотра в xterm это ровно то, что нужно, но «сырой»
  экспорт логов в файл через этот канал брать нельзя — понадобится, будет отдельный exec.
- (−) Расход: PTY на каждый таб логов дороже пайпа. При десятках одновременных follow-табов
  (не наш сценарий) стоит вернуться к spawn-каналу — механика доставки от этого не зависит.
- Для `exec`-канала ANSI из stderr/stdout снимается перед показом (`stripAnsi`): панель
  вывода — не терминал; в PTY-сессиях раскраска, наоборот, сохраняется.
